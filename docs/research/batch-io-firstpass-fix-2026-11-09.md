## 修复方式

### 1. 尾换行成为明确参数

`write_file.trailingNewline` 可选择 `preserve/LF/CRLF/none`。默认与 `preserve` 不改数据；显式选择后三者时，只把末尾连续 CR/LF 替换为恰好一个指定终止符或零个，保留正文内部换行、BOM、空格和 Tab。格式调整仅适用于普通 UTF-8 文本字符串；JSON、Office、二进制、非法参数在写入前拒绝。

例如 `data:"38", trailingNewline:"LF"` 由执行层一次产生 3 字节的 `38\n`，不再依赖模型把不可见换行放进字符串，也不通过事后编辑补齐。

### 2. 精确复制直接传递源字节

新增 `write_file.copyFrom:{path,expectedHash}`，与 `data/content` 互斥。工具在工作区边界内锁定源和目标，校验源版本、目标版本、文件身份与大小，直接把源快照字节写到暂存文件，再发布；不经过模型转述或格式处理器。

新目标默认 `missing`；覆盖必须提供目标最新版本。复制只允许省略尾换行策略或 `preserve`。源变化、目标冲突、同路径/硬链接、越界、超限、取消都会拒绝发布或按既有回滚机制记录实际结果。成功回执给出 `sourceExpectedHash`、目标 `sha256` 和 `copyVerified:true`。

因此，BOM、CRLF、末尾空格、多个尾空行及二进制不需要再穿过模型生成的正文。仍保留旧 `data` 和 `content` 别名写入兼容。

### 3. 用实际写入事实完成验收

成功 write/edit 回执增加 `byteLength`；有效 UTF-8 内容增加 `trailingLineEnding/trailingNewlineCount`，不超过 256 个 UTF-16 字符时附完整 `textPreview` 与完整标记。这些事实和 hash 来自同一次磁盘快照，不按入参猜测，避免为了确认几个字节逐文件读回。

同时修复 edit 的 `expectedHash` 曾来自内存预期、`sha256` 来自磁盘快照的不一致。新事实与短预览不会作为额外字段写入变更 SQLite 或 change 对象；正常工具历史仍保留模型实际收到的回执。

### 4. 对齐提示与验收

提示明确区分“生成新内容”和“复制现有字节”，删除必须重新转述全文、再逐个修复副本的旧指引。独立写入仍同响应提交，底层仍按序发布，版本、权限和取消机制保留。

新验收要求：**首写参数、首写成功回执 hash、最终磁盘字节三者一致**；文本批次必须覆盖六个不同目标，禁止后续 edit/再次 write 纠错。复制必须引用源修改成功后的版本，且第一次目标写入即正确，不能用最后结果掩盖先错后改。
