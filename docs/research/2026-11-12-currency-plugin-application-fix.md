# 可操作货币换算器：问题修复与实际验收

用户记录：2026-11-12 00:31 导出的「@插件管理 请帮我创建一个自定义插件：做一个可操作的货币换算器」，共两轮。本文接续此前定时器复盘，不用旧时间工具实验代替这次需求验收。

## 已确认的问题

1. 交付方式没有满足「可操作」：Agent 直接把需求解释为聊天工具，平台没有从插件列表进入的正式操作页。第二轮六次工具调用成功只能证明函数可执行。
2. 创建失败只显示 `Invalid`，丢失 `manifest.id` 的字段路径与规则。Agent 先尝试了下划线 ID 后自行猜测修法。
3. 发布后尝试加载 `plugin_currency-converter_convert`，真实全局名为 `plugin_currency_converter_convert`。即使名称正确，发布也不会给当前请求的授权工具集合动态扩权。
4. 本地工程已经可运行，Agent 又多次读取、复录完整源码给创建工具；已有本地导入流程未被说明清楚。
5. `cross_table({amount:10000,base:"JPY",...})` 返回的金额正确，`unit` 却硬编码 `1 JPY 兑换`。
6. 内置汇率没有真实获取记录、来源与日期，不能因为叫「参考快照」就被理解为有效行情。只覆盖无关货币也会让原结果错误标为 `custom`。
7. 第二轮实际只有六次成功调用，最终文字却宣称覆盖一个错误分支；不能按该文字计入通过数。

## 产品修改

- 新增正式插件操作页。已发布启用的插件从列表打开，宿主按参数 Schema 生成字段、下拉选项、运行按钮，结果采用可读展示，原始回执折叠；编辑入口独立。复杂参数仍可以用 JSON。
- `GET /plugins/runtime/apps/:id?revision=N` 获取固定发布修订；`POST /plugins/runtime/apps/:id/invoke` 强制固定 revision，每次校验发布、启用、租户、权限、Schema 与内容哈希。开发测试接口仍允许草稿，不能替代正式使用。
- 正式操作页的文件产物只预览，不自动写工作区；手动使用不自动给 Agent 增加工具授权。
- 清单错误返回具体字段与命名示例。服务返回精确 `globalToolNames`、`toolNameMap`、`selectionId`、`publishedSelectionId`，派生信息不写源记录。
- 模板协议说明原生操作页的用法；新增标准货币换算工程，中文字段和币种枚举由 Schema 描述，明确需要用户提供汇率。示例金额按十进制整数算法计算四舍五入，不虚构实时行情。

该实现是宿主生成的原生操作表单。作者任意 HTML/React 页面、后台调度与持久服务仍需独立扩展契约，本文不把这些未实现的能力计为完成。

准备的 v1.0.1 修复：单位随金额变化；金额/币种字段标题与枚举；人民币按「元」查询；汇率标为演示值；自定义/混合来源区分；禁止修改 USD 基准为非 1；独立工程改用标准测试驱动。没有为其伪造联网行情功能。

独立复核又在原插件中重现：`1.005 × 3` 错舍为 `3.01`、同币种指定汇率 2 仍执行、正小汇率显示为 0。最终修复按十进制整数分数乘除再 half-up 舍入，拒绝同币种错误汇率及无法安全表示的金额，保留正小汇率展示，并整体重写矛盾的 README。直接汇率保留输入精度，表达式仅在显示值精确相等时用 `=`，舍入或近似时用 `≈`，避免大金额乘截断汇率产生看似错误的等式。

## 真实 AI 实验发现的验收盲点

使用原句「请帮我创建一个自定义插件：做一个可操作的货币换算器」，不注入协议、源码、Schema 或调用顺序。首次隔离实验在真实 Electron-as-Node 宿主完成模板发现、1 次创建、3 例批量测试、发布及聊天/正式操作 API 调用；普通金额得到 728、1800、0。但源码复查发现 AI 重写了模板的精确算法，改用浮点乘法加 `Number.EPSILON`。这次普通成功不能代表完整验收通过。

[首次原始记录](../../.tmp/plugin-acceptance/natural-ai-currency-electron-2026-11-11T16-54-28-181Z-633eea2e/report.json) 保留最初普通用例通过结果；[扩展审查](../../.tmp/plugin-acceptance/natural-ai-currency-electron-2026-11-11T16-54-28-181Z-633eea2e/expanded-review.json) 对同一发布修订的正式路由实际验证，3 项边界均失败：小数乘法得到 3.01、同币种错误汇率未拒绝、超出最小单位安全范围仍返回数值。因此该次最终结论为 **不通过**。没有修改源码后冒充原句生成成功。

随后加强产品模板协议：基于模板做必要修改、复用已验证的实现、保留边界案例；货币工程增加 `1.005 × 3 = 3.02` 示例及明确的精度/同币种/范围说明。自然实验驱动增加这些独立边界，任何一项错误都判整轮失败。脚本的静态文案审计还修正了「不是只能聊天」的否定句误报，[更正记录](../../.tmp/plugin-acceptance/natural-ai-currency-electron-2026-11-11T16-54-28-181Z-633eea2e/currency-delivery-review.json) 不覆盖原始证据。

第二轮在上述加强文字指引及最终精度模板下重跑，仍然失败：[完整记录](../../.tmp/plugin-acceptance/natural-ai-currency-electron-2026-11-11T17-14-21-965Z-0e428ddb/report.json)。模型再次重写算法，其自选的 8 例批量测试最终全绿，但独立验收 8 项仅 4 项通过，小数精度、同币种错误汇率、超大结果和最小单位 Number 往返精度均失败。**仅靠提示 AI 不重写，不能保证模板复用。** 因此进一步实现由宿主直接创建模板工程的路径，AI 只选择模板和元数据，不再搬运算法源码。

### 宿主模板创建与最终原句验证

`plugin_create` 现在接受互斥的两种输入：匹配模板使用 `{templateId,id,name?,description?}`，自定义实现使用完整 `{manifest,files}`。模板 ID 必须来自内置白名单，插件 ID 独立校验；混传、未知模板和非法元数据在批准前拒绝。宿主同步清单、package 和 README 元数据，核心实现、案例和测试驱动原字节复制。准备批准时封存完整源码，批准后或重启恢复时不再次读取模板。新增 19 项回归覆盖所有模板业务示例、输入拒绝、精度边界、批准参数变更及模板后续变化隔离。

第三轮仍使用同一句自然需求，[原始完整报告](../../.tmp/plugin-acceptance/natural-ai-currency-electron-2026-11-11T17-24-18-836Z-e397e9b5/report.json) 通过：**1 次创建，0 次创建失败，8/8 独立业务检查通过**。创建参数含 `templateId:"currency-converter"`，`suppliedSourceFiles:[]`；[逐字节源码对照](../../.tmp/plugin-acceptance/natural-ai-currency-electron-2026-11-11T17-24-18-836Z-e397e9b5/template-reuse-review.json) 证明核心源码、5 个标准案例和测试驱动与本轮封存模板相同，没有人工修复后冒充自然生成。

独立业务检查包含：真实 AI 使用所选插件得到 728；正式操作 API 得到 728、1800、0、3.02；同币种错误汇率、超大结果、最小单位转 Number 不一致均明确返回业务失败。模型自己另执行 6 例测试但未提供 `expected`，仅算执行验证，不计作 6 个独立业务断言。模型只读取模板列表后选择模板，不读取完整详情也是有效的宿主复用；[审计更正](../../.tmp/plugin-acceptance/natural-ai-currency-electron-2026-11-11T17-24-18-836Z-e397e9b5/corrected-audit.json) 分别记录目录发现、详情读取缺失及宿主模板创建，保留原报告。
