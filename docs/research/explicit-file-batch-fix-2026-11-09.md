# 显式批量文件读写修复与验证

日期：2026-11-09。引擎 `D:\dev\ai-agent-engine`，前端 `D:\dev\aether-code`。

## 问题与结论

生产会话的三条读取实际来自三个模型响应。输入分别为 17,188、19,357、21,807 tokens，合计 58,352；不是前端把一轮账单累加三次。原引擎已经能等待同一响应中的多个工具全部结束，但模型有时每轮只选一个文件。原有“同轮批量”提示不能稳定避免这种情况。

本次为已有工具增加显式文件清单。模型现在能在一个工具调用中提交所有已知独立文件；引擎执行并合并一份结果，下一次模型请求携带完整结果。没有用隐藏或折叠工具记录冒充节省请求。

## 实现

```json
{"files":[{"path":"a.txt"},{"path":"b.txt"},{"path":"c.txt"}]}
```

上述为 `read_file` 的批量参数。`write_file` 各项仍使用原 `path/data/copyFrom/expectedHash/trailingNewline` 合同；`office_inspect` 各项使用原 `path/expectedHash/contentOffset/contentLimit` 合同。每批 1–16 项，单文件参数和 `files` 互斥，原单文件调用兼容。

- **读取**：共同预算内按文件大小分配容量，小文件读全，剩余容量供大文件分页。逐文件保留路径、版本、成功/失败和续读游标。返回完整 JSON，不将被截断的 JSON 或部分内容伪装成全文。
- **写入**：先全批校验参数、工作区路径和权限，再顺序落盘。拒绝重复/别名目标、祖先目标冲突和批内复制依赖。不是跨文件事务；部分失败或取消仍保留已落盘文件的变更记录及真实哈希，只重试未完成项。短文本完整预览在预算容纳时返回，避免为确认换行重复读取。
- **Office 检查**：全批预检，最多两个文档同时解析；每个文件独立版本和预览分页。只读子代理仍不能借批量接口写入。
- **上下文**：旧的成功批量长文本写入也可在模型请求中投影成可恢复索引，原归档参数与变更回执保持完整；失败、取消、未确认的批次保留原参数。
- **预算**：内部调用上下文的预算隔离不写入数据库，不通过模型参数抬高上限。工具清单没有增加新工具名，主子代理共用已有接口。

主要代码：`src/tools/file/file-batch.ts`、`src/tools/file/super-file-tool.ts`、`src/tools/office/index.ts`、`src/core/agent-loop/tool-output-limit.ts`、`src/core/utils/completed-write-history.ts`。执行协议及紧凑工具说明已同步。

前端已同步适配：工具摘要显示“a.txt 等 3 个文件”；读取详情按每项呈现成功、失败、取消、分页及 Office 警告。批量不作为一个文件打开，不套用首文件行号。沿用现有样式，没有修改 token 累计算法或 IPC。对应代码位于 `contrib/chat/tool-file-args.ts`、`tool-names.ts` 和 `contrib/work/work-activity-presentation.ts`、`work-message-timeline.ts`。

## 真实模型结果

使用数据库中已有 `deepseek-v4.1-flash-1017` 配置，通过真实 Work HTTP 路由运行隔离测试；生产配置只读，测试使用独立数据库和工作区。没有重启当前 Aether，没有改生产会话。每场景最多 8 次请求、120 秒、100,000 输入 tokens 的评估保护，未触发额度或超时保护。

以下三个文件任务使用普通需求描述，没有在用户提示中强制指定 `files` 参数。请求数来自出站 `fetch` 记录；回传校验比对完整工具结果的字节数和 SHA-256。

| 场景 | 工具行为 | 实际模型请求 | 输入 tokens | 输出 tokens | 结果 |
|---|---|---:|---:|---:|---|
| 三份小文本读取、变换、写入 | 1 次三文件读 + 1 次三文件写 | 3 | 30,277 | 298 | 原件不变、三个输出和总和正确、两份完整批结果进入各自下一请求 |
| 六份小文本读取、变换、写入 | 1 次六文件读 + 1 次六文件写 | 3 | 32,489 | 436 | 六份输出逐字节正确；完整回传；无需逐文件读回校验 |
| 三份 DOCX/XLSX/PPTX 检查 | 1 次三文件 `office_inspect` | 5 | 55,591 | 445 | 内容、标识及数值正确，原文件字节不变，完整检查结果进入下一请求 |
| 身份问候回归 | 无工具调用 | 1 | 9,197 | 44 | 直接回答，首请求仍低于 10K |

三次请求的含义是：①首次决策；②整批读取结果回传后决定写入；③整批写入结果回传后回答。三文件和六文件都没有每读/写一个文件再发一次上下文。

Office 的五次请求包含目录查看、技能读取、工具定义加载和一次批量检查，**不等于五次文件检查**。此处仍有减少前置回合的空间，本次没有把它宣称为三次请求。文件任务首请求输入为 9,259–9,274 tokens；后续输入包含新增内容，可以超过 10K。

本轮四个场景共 **12 次实际请求，127,554 输入 + 1,223 输出 = 128,777 tokens**。没有严格同任务旧版 A/B，因此不声称实测固定节省百分比；旧六文件专项还包含额外交付回合，不能直接当等价基线。

Office 原验收器只识别“甲组：12”形式，未识别带表头的结果表格，出现一次 `factsCorrect=false`。已补按明确列及每文件行匹配的检查，并加入错误数值、交换列、缺行、重复行及矛盾表格负例。原证据不改；离线复评全部通过，无新增模型请求。
