# 回退后旧子代理统计重新出现

## 现场证据

用户在 Work 模式回退后重新发送消息，界面在当前执行过程下方出现孤立的 `640.3k tokens · 4m57s`，并把它计入顶部会话总计。

本次仅以只读方式检查本机 Aether 的 SQLite 和会话 JSONL，没有修改用户数据库、历史或工作区。

- 会话：`work-home-aeeb6b58-93a9-4b9f-aa1f-0366a3836707`。
- 被回退轮：`fda0caf3-c74b-4514-92ee-a5bcf18a79ce`。
- 该轮两个子代理用量为 `143847` 与 `496410`，合计 **640257 tokens**，正好格式化为截图中的 **640.3k**。
- 最早创建时间 `1794285633819`，最晚结束时间 `1794285931184`，跨度 **297365 ms**，正好显示 **4m57s**。
- JSONL 已记录对该轮的截断及用户消息删除；SQLite 当前仅保留重新发送后的 root run 和两个新子代理。

这些数值证明红框来自被回退的旧子代理，而不是新模型请求、文件回退报告或随机文本。JSONL 物理文件保留旧追加记录属于日志机制，读取时的 tombstone 已将其排除，不应再作为当前会话展示。

## 原因

前端 `useChat` 在清空历史时调用 `forgetSubagentSession` 和 `forgetCommandSession`，但回退、截断、重试及删除单轮成功后没有执行同样的缓存失效。

恢复快照随后把权威消息与内存中的子代理合并。`attachSubagentRuns(..., true)` 为找不到原消息的子代理补建助手消息，这本来用于恢复中断时尚未写全的有效派发记录，却也把已经删除的旧子代理重新挂回对话。由此出现无正常正文的统计行，并污染本地用量增量与耗时。

## 修复与验收范围

- 历史变更成功后、重新读取快照之前，使该会话的子代理及命令缓存失效。
- 使用既有代际校验拒绝回退前发出、回退后才完成的旧请求。
- 从新快照恢复仍然保留的历史，不能把合法的前轮子代理或其他会话误删。
- 部分文件回退、取消确认或失败不得冒充历史已删除。
- 覆盖回退后立即重发：旧卡片、旧统计、旧成果引用不再恢复，新运行使用自己的记录。

前端新增统一的 `history-runtime-cache.ts`，各历史变更入口仅在服务端确认成功后调用。命令缓存的失效保留 Code/Work 的订阅所有者，避免清理后无法接收仍有效的命令记录。

## 同时修复的压缩边界

这部分是独立复现的问题，并非截图中 640257 tokens 的直接来源：

- 整轮删除原先逐条删除当前紧凑消息列表，可能漏掉 JSONL 归档中的同轮消息和用量；现在对已验证的租户、会话执行整轮删除。
- 整轮回退通过稳定轮次 ID 找到已被压缩隐藏的子代理派发；从轮内补充消息截断时仍保留之前派发的子代理。
- 删除子代理调用引用后，仅清空没有任何存活引用的子会话。多个调用共用一个子会话时保留完整上下文；本次没有实现把该共享上下文倒回到某次子代理调用边界。

## 验证

- 引擎：破坏性历史操作、JSONL/SQLite 用量、文件回退、历史展示、命令生命周期、工具派发锚点共 **120 项通过**。
- 前端缓存及回退协议：**15 项通过**，覆盖现场同值残留、其他会话隔离、旧目录/详情/命令请求迟到、双模式订阅保留、撤销成果恢复与部分回退失败。
- Electron 完整交互：**3 项通过**，包括回退后重发、部分回退失败后重试、没有文件改动的回退。新用例使用有界子代理目录，确保不会由全量列表刷新偶然掩盖缓存缺陷；会话累计按 **641.5k → 1.2k → 3.3k** 变化，保留轮为 1.2k、新轮为 2.1k，重载结果一致。
- 两个仓库的类型检查及构建通过，相关测试合计 **138 项通过**。前端测试固定使用独立构建副本，避免其他并行任务重新构建影响结果。
