# 记忆注入、缓存与辅助调用审计

日期：2026-11-09。范围：当前引擎源码、Aether 客户端字段使用、一个本地记忆库的只读聚合快照。没有修改生产代码、调用真实模型或输出个人记忆正文。

## 结论

记忆存在两条注入路径，都仍在 system 中。数据库召回每个用户 HTTP 请求执行一次，同一 ReAct 运行内保持固定；跨用户回合的召回变化会改变历史之前的前缀。之前将运行时状态移到 requestContext 的修复尚未覆盖记忆。

数据库召回有摘要预算，并非把完整记忆库注入。但内联 XML 没有同等预算；辅助模型调用、前台向量补齐和运行中开关失效也需要分别处理。

## 实际链路与证据

1. `src/api/http/routes/chat.ts:759` 先解析持久偏好及会话 override。默认无授权；全局记忆与会话记忆独立。环境变量 `ENABLE_LONG_TERM_MEMORY=false` 强制关闭，true 不自动开启授权。
2. `chat.ts:1303` 每次用户请求调用 `buildMemoryRecallBlock`，与 RAG 检索并行。
3. `src/middleware/memory/extractor.ts:438` 先调用一次聊天模型生成检索关键词或 NONE，再生成一次 query embedding，分别检索授权 scope。
4. 每个 scope 向量最多取 10 个锚点；不足 5 个时补关键词候选，锚点最多 15 个。首锚点扩展两跳，其余扩展相邻节点。图扩展候选数目前没有上限。
5. `extractor.ts:397` 只渲染 summary 和来源 ID、会话、turnId、固定记录时间、标签；不注入 detail、向量或完整聊天记录。总预算 `min(8000, contextWindow × 8%)` 个估算 tokens，单条上限 2000，原文保留。
6. `src/core/chat-system-prompt.ts:24` 将召回块拼入 system。选集随查询、新记忆、修改和排序而变化，可能使跨回合缓存从该处失效。固定记录时间不是每次变化的时钟。
7. `chat.ts:1084` 还有客户端 `inlineMemoriesXml` 路径：有效 scopes 非空就将整个 trim 后 XML 拼入 base system，没有逐条 scope 过滤、去重或召回预算。当前 Aether 源码未发现发送该字段，其他客户端仍可使用此协议。
8. `chat.ts:1720` 在回答结束后异步抽取本轮用户/助手文本，不会直接抽取工具结果正文。长文本按预算分块，每块额外一次模型请求，并可能生成 embedding。并非每轮重新抽取全部会话历史。

## 额外成本与质量问题

- 路由模型请求上限 100 输出 tokens；即使空库或简单寒暄，也要经过模型路由才能提前返回。目前没有基于空库的短路。
- 路由、抽取调用没有传入根请求的 `onRequestAttempt`，返回 usage 也没有汇入当前问答统计。独立 embedding 服务只返回向量，未暴露用量。主问答统计因此不是全部记忆辅助请求的成本账单。
- 召回在每个 scope 中等待最多 20 条旧记忆的向量补齐；补齐是 batch，但处于回答开始前的等待路径。已有并发去重，没有失败退避。
- 最终渲染按 importance、timestamp、strength、ID 排序，未保留直接检索相似度，图邻居可能挤占更相关的直接命中。
- 关键词、向量边界候选和标签读取缺少完整的确定性次排序。给最终渲染排序不能修复更早 LIMIT 所选候选的不稳定。
- 无原生向量函数时，向量回退会加载授权 scope 中的 embedding_json 再在进程内计算距离；注入预算不能限制这一步的内存峰值。

## 生命周期与子代理

- 普通偏好 API 写入数据库，但不会刷新当前运行的 scopes 快照和已组装 system。下一次 HTTP 请求才重新解析；当前运行后续工具和异步抽取仍可能使用此前授权。
- 删除节点立即作用于数据库；提取协调器和成功工具回执可以防止在途抽取直接复活删除项，但不会撤回已注入本轮 system 的文本。删除记忆与删除原始聊天记录是不同操作。
- 抽取协调器只存在于进程内，抽取任务不能跨进程重启续跑；已写入节点持久保存在本地 memory.db。
- 子代理继承父 scopes 快照，使用自己的 childSessionId。会话私有记忆按 child 隔离，全局记忆按租户共享。
- 子代理当前没有根会话同等的自动召回/自动抽取入口，也不复制父召回块；它可以调用获准的记忆工具。继承父聊天历史不等于继承父 system 中的临时召回块。

## 建议落地顺序

1. **先保护缓存前缀**：system 仅保留稳定的记忆使用规则；数据库召回和客户端内联数据统一移入历史后的临时 requestContext。沿用现有 adapter 尾部协议，确保预算、重试、压缩和最终收尾请求均计入。保持不持久化、不制造用户回合的行为。此改动保护之前的前缀，不会让记忆 tokens 免费，也不自动减少每次携带的数量。
2. **统一控制注入量**：两条路径共同经过预算、来源和权限检查。建议将常规摘要目标设为约 1000–2000 估算 tokens，再按任务及模型窗口评测；这是建议值，当前上限仍为 8000/8%。详情通过 recall/search_history 按需查阅。保留直接命中优先级，并限制图候选数量；数据库原文不删减。
3. **减少等待和辅助请求**：授权 scope 空库直接返回；为明确寒暄提供保守短路。将向量补齐移出前台关键路径，增加失败退避。逐步采用可观测的本地检索，确有必要时再调用模型改写查询，不能为了省调用让语义召回静默失效。
4. **补完整失效机制**：新增、修改、删除、标签、设置和 scope 变化都维护独立版本，并在每次请求边界检查。现有 extraction-coordinator revision 仅覆盖删除且会清理，不能直接当作完整召回缓存版本。不可直接用简单 TTL 忽略删除或关闭。
5. **完善成本统计与子代理一致性**：辅助调用记录用途、来源 run 和实际 usage，与当前上下文占用分开显示。根/子代理共用授权召回入口；父会话私有记忆若要共享，必须有明确授权及传递范围，不能直接按 parentSessionId 越过隔离。

仅改变引擎注入位置不要求前端修改。若展示召回数量、记忆占用及辅助调用成本，则需要扩展统计协议并同步 Aether。
