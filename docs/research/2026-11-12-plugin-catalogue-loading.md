# 插件目录与 @ 菜单加载性能

## 原因

`/toolkits` 的插件目录与 Agent 配置工具定义原先逐个调用 `PluginService.snapshot`，同步读取全部插件源码、依赖目录，计算文件树哈希并重新校验参数结构。目录展示因而承担执行前校验的成本；这些同步操作也会延迟同一 Node 事件循环中的 Agent 列表读取。

前端每次挂载引用菜单还会清空并重取 Agent、工具包目录。插件宿主启动和资源变更则会读取所有已启用插件的应用，包含没有界面贡献的纯工具插件；原实现等待全部应用返回后才注册导航，慢插件会拖住其他插件。

## 修改

- 引擎新增 `listPublishedMetadata`，目录和配置工具定义使用已发布元数据，不遍历执行文件。存在新草稿时读取对应已发布快照元数据，核对版本与元数据哈希，避免草稿覆盖当前可用工具。发布、工具注册、执行与页面内容读取仍使用完整快照校验。
- 前端只为 Agent 的 ID、名称、描述和轻量工具包目录增加共享缓存。成功值有效期 30 秒，工具包最多保留 32 个范围；并发读取复用同一请求，失败不缓存。引擎、账号、会话、主 Agent 与工作区分别隔离。真实管理变更会立即失效，已失效的旧请求不能回填。
- 插件宿主按来源、已发布修订和哈希保留已有注册，只加载有变化的应用；纯工具插件不预加载应用页面。存在新草稿时继续读取实际已发布应用，避免遗漏旧版界面。各插件完成后独立注册，启动时同轮来源和就绪通知合并。
- 工具包目录读取失败时提供明确重试入口。

## 隔离测量

使用 12 个实际插件项目建立独立存储，重依赖场景包含 1,794 个来自先前 GitHub 隔离导入的依赖文件。每项测量执行三次，没有读取正式环境数据库或凭据。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 普通 12 插件目录 | 102–108 ms | 16–18 ms |
| 重依赖目录 | 787–821 ms | 23–24 ms |
| 重依赖目录期间排队的 Agent 列表读取 | 789–823 ms | 26–28 ms |
| 重依赖目录同步文件读取 | 1,966 次 | 12 次 |

Agent 耗时是与目录操作同时排队、通过实际隔离 SQLite AgentStore 执行列表查询的观测值，包含事件循环等待，不是正式窗口的 HTTP 网络计时。测量说明同步文件扫描可以导致截图中的 Agent 加载等待；不能把此数值视为用户机器每次等待的完整耗时。

完整应用首次读取仍有校验成本：重依赖场景同时读取 12 个应用耗时 729–793 ms。前端本轮消除了纯工具插件的无关预加载与未变化应用的重复读取；首次打开实际应用和执行工具仍保留相应校验。

## 验证

- 引擎 43 项相关目录、元数据、集成及运行测试通过，包含草稿隔离、停用、白名单、损坏元数据、源码篡改后仍拒绝执行与发布；typecheck 通过，源码在隔离输出目录完整编译通过。
- 前端 typecheck 与 build 通过；25 项针对性回归通过，最终构建另复跑 3 个真实 Electron 加载用例通过。
- 实际窗口中延迟一个应用的响应，快速插件导航仍先出现；纯工具插件应用读取次数为 0。
- 延迟自定义 Agent 响应，插件工具包可先显示；同范围连续关闭重开 `@` 三次，请求数不增加且不闪加载文案。
- 通过真实管理开关停用插件，菜单及时更新，其他未变化插件的应用不重新读取；已有宿主生命周期测试继续覆盖禁用卸载、版本替换、服务、失效异步结果及主题同步。

专项用例为同级前端仓库的 `e2e/plugin-catalogue-loading-ui.spec.ts`、`e2e/reference-catalogue-cache.spec.ts`，引擎用例为 `src/plugins/__tests__/catalogue-loading.test.ts`。性能原始测量保留在 `.e2e-tmp/plugin-loading-20261112/{before,after,heavy}.json`；前端窗口运行证据位于该仓库对应 `.e2e-tmp/plugin-loading-20261112/`。

开发启动脚本将引擎固定为启动时的独立编译快照；现有开发窗口需要在当前任务结束后重新运行 `npm run dev` 才会加载新的引擎实现。正式安装版需要重新打包客户端和引擎。
