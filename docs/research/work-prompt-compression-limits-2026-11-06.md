日期：2026-11-06。与多维报告同一数据库模型配置，真实 Work 路由；总输入包含缓存。最终普通短请求约 5.4K，以下测试说明这个数字的适用范围和代价。

## 最少常驻工具试验

从冻结 v2 复制隔离实验源码，仅将常驻集合由 14 个定义改为 `plan_update` 和 `load_tools`。计划控制保留以恢复持久计划；其余能力和参数都仍可加载，权限未改变。

| 同题场景 | v2 首轮 → 极限首轮 | 极限结果 | 总调用数 v2 → 极限 | 总输入 v2 → 极限 |
|---|---:|---|---:|---:|
| 身份介绍 | 5,423 → 3,239 | 通过 | 3 → 3 | 6,126 → 3,887 |
| 文件搜索 | 5,435 → 3,259 | 通过 | 4 → 5 | 11,751 → 11,706 |
| Excel 公式 | 5,461 → 3,271 | 通过 | 10 → 13 | 90,828 → 92,564 |
| 已完成子代理续用 | 5,473 → 3,293 | 未通过 | 11 → 8 | 59,551 → 25,116（任务未完成，不算节省收益） |

极限版的子代理记录只有一轮，未调用 followup，没有第二个答案，最终文本偏离原任务；v2 同题三次通过。一次失败不能证明问题唯一由常驻集合大小造成，但已经足以拒绝把此候选当成“效果不丢”的默认实现。搜索基本没有总 token 收益，Office 增加调用且总输入略高，也说明不能单独优化首轮数字。

## 文言文试验

只替换公共执行协议，其他工具、模型、参数、运行逻辑与 v2 相同，单独冻结源码，不覆盖生产实现。全文候选及约束映射在 `.e2e-tmp/prompt-compression-20261106/system-classical-candidate/`。

| 指标/场景 | v2 明确表达 | 文言候选 |
|---|---:|---:|
| 公共执行协议字符 | 5,689 | 1,600（减少 71.9%） |
| 公共协议本地 token 估算 | 1,435 | 1,685（增加 17.4%） |
| 身份回答实际首轮输入 | 5,423 | 5,354（仅减少 69，约 1.3%） |
| 文件复制实际首轮输入 | 5,457 | 5,388 |
| Excel 实际首轮输入 | 5,461 | 5,382 |
| 子代理续用实际首轮输入 | 5,473 | 5,396 |
| 四项实际行为 | 身份/Excel/续用通过，复制失败 | 同样 3/4；复制仍失败 |

字符、字节、本地估算和模型实际 token 不是同一指标。不同测试会话/路径/动态环境也贡献少量输入差异，因此 69 tokens 不能当作严格受控的语言效率定律。

本轮没有采用文言默认版：收益约 1%，尚无比 v2 更广的功能证据；“足据”“简览”“迟信”等缩写提高了规则复核和歧义成本。用户可见回答仍为中文。真正的大幅收益来自避免每次重复发送暂不使用的全部工具结构，不来自删除空行或把句子改古雅。

## 代价、失败与后续界限

按需加载会增加一次或多次模型往返。矩阵总调用数 87 → 88，不是每项任务都更快。所有工具都加载、长历史、长附件、大量 MCP 或自定义提示词仍可超过 10K；没有为过线截断用户自定义规则或偷偷关闭能力。

模型行为的剩余失败也构成当前极限：逐字节复制尾换行与记忆独立副本清理，在原版和最终版都未通过。本轮没有用自动批准命令、削弱权限或放宽断言掩盖这些问题。最终版修复了早期候选的 Office 纠错退化，精确单元格/公式缓存连续 3/3 通过。

长输入首次诊断只拿到 HTTP JSON 错误；随后保留了 raw response 并加只观察的 onError hook，定位 `SQLITE_ERROR: Expression tree is too large (maximum depth 1000)`。同 1200 行在冻结基线复现；缩为 600 行后仍超过 10K，并成功找回 `NEAR_START_Q7L9` 和 `NEAR_END_R2M8`。未把这次 SQL 故障解释为模型欠费、上下文耗尽或加载失败。

本次没有进行 256K 整窗压力、真实浏览器 GUI、外部 MCP 服务、外部发送动作或所有办公格式的视觉验收。子代理自动压缩、重启恢复、消息投递和并发边界有实际存储/执行器回归证据，不等于本轮已用付费模型跑过每个超长恢复排列。
