# 项目调研中的代码图失败、子代理结果截断与 Token 用量审计

日期：2026-11-09。引擎基线：`9d8fee2`。前端：`D:\dev\aether-code`；被调研项目：`D:\web\wuzu-client`。

后续修复已实施，见 [修复与验证记录](codegraph-subagent-repair-2026-11-10.md)。以下保留审计时的现场事实与问题分析。

本次核对用户导出的会话、补充截图、实际运行 JSONL、子代理运行记录及当前源码。只读检查现场数据库；没有调用真实模型，没有重建索引、清理 WAL、修改项目忽略规则或重启 Aether。本文件是调查结论，下面的修复方案尚未实施。

## 结论

1. **代码图失败的直接原因是引擎为 research 子代理设置的 64 MiB 快照限制。** 现场主库已经达到 167.777 MiB，当前没有 WAL；不是 SQLite 的通用容量限制，也不是模型上下文限制。
2. **主代理与只读子代理打开索引的路径不同。** 普通路径直接打开 SDK，research 路径先制作受限私有快照。同一只读路径下，正常索引的 `status`、`files`、`search` 都要经过这道门禁，不能解释为它们各有不同容量阈值。
3. **存在影响主代理判断的结果丢失。** 两个子代理生成了完整结果，但交给主代理时被静默截为 8,192 UTF-8 字节；Aether 展示层还会再次限制为 4,096 字节。完整文本仍在子会话 JSONL 中，并非模型没有写完。
4. **107 万 Token 是 35 次模型请求累计的输入与输出。** 该子任务单次上下文峰值为 47,934 Token，输入缓存命中约 93.12%。统计未发现重复累计；效率问题主要来自多轮目录探索、分页读取及每轮再次携带历史工具结果。
5. **截图中顶部“成功”与单步失败能够同时成立，但文案需要区分层级。** 续派接纳成功、任务最终完成和单条工具执行成功是不同状态。导出还存在忽略分页覆盖范围、将已加载工具数当总数的问题。

## 1. 代码图为什么不能用

### 1.1 实际索引大小和构成

现场文件：`D:\web\wuzu-client\.ae\codegraph.db`。

| 项目 | 只读检查结果 |
| --- | ---: |
| 主库 | 175,927,296 bytes，167.777 MiB |
| SQLite 页 | 42,951 × 4,096 bytes |
| 空闲页 `freelist_count` | 0 |
| WAL / SHM | 当前不存在 |
| 文件 / 节点 / 边 | 2,105 / 44,450 / 162,257 |
| 索引元数据 | `index_state=complete` |

表及其索引的实际占页归组如下。现场 SQLite 没有 `dbstat` 扩展，因此采用只读 B-tree/overflow 页遍历；42,951 页均被覆盖且没有重叠。

| 归组 | 字节 | 主库占比 |
| --- | ---: | ---: |
| `edges` 及索引 | 71,262,208 | 40.51% |
| `unresolved_refs` 及索引 | 70,922,240 | 40.31% |
| `nodes` 及索引 | 24,707,072 | 14.04% |
| FTS 相关表 | 6,189,056 | 3.52% |
| vocab | 2,265,088 | 1.29% |
| 其余 | 581,632 | 0.33% |

`unresolved_refs` 有 148,231 条，状态全部为 `failed`。这是符号引用解析状态，不是 148,231 个 Agent 任务失败。SDK 的 `db/schema.sql:79` 和 `db/queries.js:2191` 明确保留这些记录，供后续 sync 新增符号时重试补边，并在来源节点删除时级联清理；failed 不计入 pending backlog，因此与 complete 不冲突。它及相关索引占约四成空间，值得研究更紧凑的索引与保留策略；**直接删除会损失增量关联能力，不能把这四成空间认定为可删垃圾**。

索引文件按顶级目录分布：`src` 1,627、`test` 223、`lobster-core` 132、`resources` 47、`installer` 32、`scripts` 29、根目录 11、`rag_eval` 3、`test-e1` 1。已索引路径中，`node_modules`、`dist`、`build`、`out`、`outputs` 为 0 项。

因此，“node_modules/dist 被误索引”“WAL 太大”“大量空闲页未回收”均不符合当前现场。检查前后主库大小和修改时间一致，没有执行 checkpoint、VACUUM 或索引写入。

另一个规则问题：项目确实有 `.codemapignore`，其中也写了排除目录；但当前安装的 CodeGraph SDK 1.6.0 使用的是 `codegraph.json` 的 include/exclude、`.gitignore` 和默认排除目录，未找到读取 `.codemapignore` 的实现。不能把修改这个文件当成已验证有效的修复。

### 1.2 限制来自引擎的研究角色保护

调用链：

```text
research 子代理调用 codegraph
  → withReadonlyCodegraph
  → codegraph-tool 按只读角色分支
  → openReadonlyCodegraphSnapshot
  → 检查主库 + WAL 是否超过 64 MiB
  → 当前主库自身已经超限，拒绝
```

关键实现：

- `src/tools/subagent/subagent-tool.ts`：只读子代理的 codegraph 执行进入只读作用域。
- `src/tools/codegraph/codegraph-readonly.ts:13`：`CODEGRAPH_SNAPSHOT_MAX_BYTES = 64 * 1024 * 1024`。
- `src/tools/codegraph/codegraph-readonly.ts:22`：只读快照实现。
- `src/tools/codegraph/codegraph-tool.ts:205`：只读快照与普通 SDK 打开的分支。

当前 SDK 的 `openSync(projectRoot)` 没有引擎可依赖的真正只读接口；打开时可能配置数据库、迁移或修复，因此不能为了研究角色直接移除隔离保护。

目前的私有快照会完整读取数据库及 WAL，连续采集两遍 Buffer 比较一致性，再写到临时磁盘交给 SDK。每次查询重新创建，未共享复用。若简单将上限提高到 256 MiB，本项目单个查询仅两份主库 Buffer 就约 335.6 MiB，尚未计入 SQLite/SDK 和其他开销；并行子代理会进一步放大资源需求。因此只提高阈值会掩盖架构问题。

例外：`status` 在同工作区索引任务正在运行或已失败时，可以直接读取内存中的索引进度；它不代表已成功打开完整索引。正常完成索引的 `status` 与其他查询仍走相同只读门禁。

### 1.3 附件中原解释哪些不成立

导出第 542、1120 行附近的 `status`，以及第 1523、1861 行附近的 `files`，均明确返回 64 MiB 失败。每个初始子代理只尝试失败一次，然后 fallback，并未反复重试代码图。

普通主代理走直接 SDK 路径，可以解释父子角色的行为差异；但顶层“代码图查询：.（成功）”省略了 action 与完整输出，不能仅凭这个摘要反推每次具体执行了什么。原回复中关于“status 能过而 search 需要大快照”的说法与源码不符；关于 WAL、依赖目录的推断也没有现场依据。

## 2. 子代理完成了，为什么主代理仍然缺信息

### 2.1 三层裁剪没有一致的完整性协议

| 层级 | 实现 | 行为 |
| --- | --- | --- |
| 引擎 runner | `src/core/subagent/runner.ts:47,365` | 输出超过 8,000 字符才截断，并在末尾追加提示 |
| 持久化 header | `src/core/subagent/store.ts:35` | 再限制为 8,192 UTF-8 字节，不追加提示 |
| Aether 展示状态 | `src/renderer/src/core/engine/subagent-state.ts:451` | 再限制为 4,096 UTF-8 字节，没有独立结果截断标志 |

字节与字符不是同一单位。中文文本可能不足 8,000 字符，却早已超过 8,192 字节；即使 runner 添加了提示，后续按字节取前缀也可能把末尾提示一起切掉。

此外，`resultSummary` 在这次现场是本次累计输出的前缀，并非单独生成的结果摘要，可能先包含执行过程说明，最后的结论更容易被裁掉。

| Run ID 前缀 | 最终 assistant 字符 / 字节 | 本次累计输出字符 / 字节 | 主代理收到的 summary 字符 / 字节 |
| --- | ---: | ---: | ---: |

两个加粗结果精确匹配“runner 字符限制，再 store 字节限制”的前缀，**均没有截断标记**。父会话 `assistant` 类型的 `subagent-result:<runId>` 正文及 metadata 与这些截断结果完全相同。因此这不是单纯 UI 显示短，而是主代理用于汇总的信息也不完整。

前两个结果虽在引擎没有截断，但仍超过前端 4,096 字节预览上限；前端源码也没有可靠的“读取完整返回结果”协议。

`outcomeText`（`src/core/subagent/types.ts:252`）、父历史 projection 和 `subagent_wait` 直接投递 summary；没有独立的结果总字节数、完整性标志或分页游标。现有 `search_history` 仅接受当前执行会话作用域，父代理不能直接指定任意 childSessionId 读取全文。完整 JSONL 尚在，并不等于主代理具有可靠的补读入口。

具体效率问题包括：把必须单读的规则文件放进批读后重试、规则摘要再次被通用输出限制截断、为规模统计枚举大量文件名、目录当文件读取、相邻分页存在重叠等。另一个业务域子任务大量逐级列目录。四个任务的总体范围有分工，并非四份相同调研；不能把全部消耗归因于“开了四个子代理”或那一次代码图失败。

四个初始子任务没有发生自动上下文压缩：配置窗口 256,000，峰值远低于其触发阈值。这符合当前压缩规则，但也说明“避免窗口溢出”的压缩策略不能代替“减少累计请求成本”的工具与历史管理。

但是，没有工具调用也意味着它只是基于已有上下文解释旧报错，没有重新验证 WAL、忽略目录或 SDK 的当前实现。因此这次回复里的推测不能算已完成现场诊断。

## 5. 状态与导出需要如何区分

- `subagent_followup` 的 `success:true` 可以只代表续派请求已接纳或排队。
- `subagent_wait` 的 `success:true` 表示观察操作成功，真实任务状态在正文及 metadata 中；它不是所有子步骤均成功的证明。
- 子代理正常给出最终回答后，整个 run 可以是 completed/succeeded，即便早先某条工具失败并已 fallback。
- codegraph 的 `success:false` 已正确传到 runner、前端状态和红叉；截图没有把这一条显示成成功。

前端可改为“已接纳”“已完成”“未完成”等具体语义，并保留“1 步未通过”；不应为了统一颜色而把已完成的调研判成整体失败，也不应让总体“成功”掩盖工具不可用。

独立的导出缺陷位于 Aether `subagent-state.ts:1329`：`exportSubagentDetails` 遍历当前 `run.toolCalls`，直接以数组长度输出工具总数，忽略 schema v2 的 `toolCount`、`includedToolCount`、`coverage.hasMore` 等信息，也没有分页补齐。由此其他场景中的“0 工具”可能只是未加载，需与本次已核实的真实 0 工具区别对待。

普通成功工具的聊天导出还省略 action 和完整回执，参数摘要优先显示 path，因而“代码图查询：.（成功）”缺少诊断所需语义。导出应按需保留 codegraph action、关键参数、状态以及覆盖水位，避免再次靠猜测解释。

## 6. 建议实施顺序与验收

### P0：恢复研究角色可用的代码图查询

优先评估 SDK 真正只读支持或受限 SQLite 查询适配层；若仍必须使用会修复数据库的 SDK，则提供有一致性保证、流式落盘、可复用的私有磁盘快照，由专用 worker 管理生命周期。不要每个查询都将完整库双份装入 JS Buffer。

主代理与子代理应使用一致的查询能力探测，明确区分“索引文件存在”“索引流程已完成”“当前角色可查询”。提前返回可操作的原因，避免每个研究子代理都先碰同一门禁。现场无 WAL 不代表未来不会有 WAL；快照实现必须覆盖活 WAL 和源库变化，不能对活库盲用 `immutable=1`。

验收：本次 168 MiB 规模库与活 WAL 场景均能查询；源工作区文件不被改写；并行查询内存受控；源版本变化后正确失效；工作区切换、越界及符号链接保护保持有效。

### P0：完整结果与轻量摘要分开

复用已落盘转录保存完整结果，并建立按父子归属授权的 `resultRef` / hash / totalBytes / truncated 协议及字节分页读取。摘要只作为摘要；主代理和 UI 都能判断是否完整并补读。引擎与前端统一 UTF-8 字节语义，截断提示作为独立元数据，不依赖可能被下一层裁掉的尾部文字。

验收：中文、英文、emoji、超过 8 KiB 和多页输出都能恢复原文；主代理可拿到最终结论；跨租户或无归属子会话拒绝访问；重启后仍可补读；预览大小不再影响最终结果的完整性。

### P1：协调工具输出、请求数与调研质量

提供目录概览/计数，减少为统计规模枚举所有路径；在工具调用前处理必须单读的规则文件；协调 read_file 分页与外层输出上限，避免刚读完又被截掉；按相关任务划分上下文，复用已有子代理。对已消费的长工具证据生成有来源、可补读的紧凑投影，并验证重要证据不丢失、提示缓存前缀不被频繁破坏。

验收需要同时记录任务正确性、请求次数、输入/输出、缓存输入、非命中输入、峰值上下文、延迟及完整性，不能只追求 UI 上的 Token 数下降。调研预算应是可观察的进度与软约束，不能为了省步骤无条件提前终止深度任务。

### P1：同步修复前端状态与导出

前端确实需要改动：结果完整性入口、导出分页覆盖信息、真实工具总数、codegraph action 以及续派/完成状态文案。引擎返回结构修复后，单改数据库或后端不能消除 4 KiB 展示截断与导出误计数。
