# 批量文件操作与模型请求次数复核

用户反馈：界面同时出现三条读取记录，累计 token 像单次上下文增长了三遍。

## 已确认的区别

一轮模型可以返回三个独立工具调用。引擎执行三次文件读取，保留各自结果/错误/版本，等整批完成后在下一次模型请求中一次提交全部结果。这里有三次本地文件操作、三条工具记录，但不应为每条结果各请求一次模型。

如果模型本轮只提出一个读取，拿到结果后下一轮才提出第二个读取，则实际产生多次模型响应和历史重放；引擎目前不会预测模型未来要读的文件，也没有把跨轮请求强行合并。

## 测试覆盖的真实边界

- 六文件专项 `batch-v6-firstpass`：首模型响应含六个 read_file，下一请求带六份结果；第二响应含六个 write_file，随后一次带回六份写回执。全场景共五次请求，另含工具加载、最终登记和答复。
- 最新 `team-token-v7` 普通办公：创建 DOCX/XLSX/PPTX 确实同一响应，但三次 office_inspect 分属第 7、8、9 个模型响应。
- 同版本双子代理办公：主代理三次 office_inspect 分属第 13、14、15 个模型响应。
- 因此“支持批量且专项通过”不等于“所有真实任务的独立读取/检查都已稳定合批”。此前办公流程验收没有把合批率列为必过项，应明确保留这个缺口。
- 本轮重新运行 ReAct 批次回归 7/7：只读同批并发、结果齐后才请求模型；写入同轮按序发布后一起返回；保留失败、取消、同文件依赖和审批边界。未为此次取证再次调用付费模型。

## 记账链路

ReAct 按模型响应累计一次 usage；同一批仅第一条 assistant 工具行存 usage，后续条目 tokens=0。流式上下文快照可以更新多次，但不带累计计费字段。HTTP 与流投影覆盖累计快照，不逐帧相加。工具结果回调本身不调用模型、也不增加模型 usage。

已检查的引擎路径未发现按三个工具重复记账。前端也使用实际 `replayMessages → sessionUsageTotal` 复放了这次生产 run，footer 得到 **1,072,392**，与持久用量一致。三次独立读取含输出共 **59,268**，同批两读含输出共 **27,578**，均未乘工具数。三读/三写、重复累计帧、历史恢复、快照覆盖、补充拆段、权威用量锚点共 **17/17** 离线断言通过。证据：`D:/dev/aether-code/.e2e-tmp/batch-usage-audit/result.json` 及同目录 `probe.ts`。本轮没有修改产品计费逻辑。

这些证据排除了所复放路径的工具数重复计费；不能用“界面同时出现三条”证明是一个模型请求，也不能把三个真实模型响应的消耗改成一个来制造节省。

优化应针对模型规划与批量合同：已知且独立、大小符合预算的文件应一次给出读取清单，整批回传；不同目标且内容已定的写入同理；只为真实依赖、分页/容量限制拆批。验收需要同时核对调用批次、模型响应/实际网络请求、计费次数，不能只核对文件是否生成成功。
